5 Anforderungen und Ziel (Soll-Zustand)

Es soll ein Infosystem erstellt werden, mit dem Cucumber/Gherkin Feature-Dateien verwaltet, ausgeführt und ausgewertet werden können. Die Feature-Dateien werden vom "Cucumbergenerator" (Web-Tool) erzeugt und als .feature-Dateien auf dem Server im Verzeichnis $MANDANT/ow1/cucumber/features/<arbeitspaket>/ abgelegt.

Das Infosystem soll folgende Kernfunktionen bieten:

  • Verwaltung: Feature-Dateien vom Filesystem einlesen, nach Tags/Ordnern filtern, anzeigen
  • Konzeptimport: Reiter zum Hochladen/Importieren von Feature-Dateien in einen gewählten Arbeitspaket-Ordner (Reiter erst sichtbar wenn Ordner gewählt)
  • Ausführung: Einzelne oder alle Features manuell ausführen (interner FOP/Java Step-Runner)
  • Cron-Anbindung: Automatische Ausführung per Cronjob, filterbar nach Tags (z.B. @nightly, @regression)
  • Auswertung: Pro Feature-Datei ein Ergebnis-Datensatz (DB: CUCUMBER_RESULT) mit Testlauf-Historie in der Tabelle und berechneten KPIs im Kopf (durchschnittliche Dauer und Erfolgsquote der letzten X Läufe, X einstellbar)

Architektur-Übersicht:

|  Cucumbergenerator (Web)  | ----> |  .feature Dateien                    |
|  erzeugt Feature-Files    |       |  Ablage: $MANDANT/ow1/cucumber/     |
+---------------------------+       |          features/<arbeitspaket>/    |

6.5 Umsetzungsbeschreibungen

6.5.1 Datenbank CUCUMBER_RESULT

1 Datensatz pro Feature-Datei. Suchschlüssel = GUID (eindeutig, aus dem Tag der Feature-Datei, z.B. @guid-a1b2c3d4).

  • Kopf: Feature-Metadaten + berechnete KPI-Felder
  • Tabelle: Testlauf-Historie, jede Zeile = 1 Testlauf, neueste oben
  • runStepDetails enthält ein JSON mit den Ergebnissen auf Step-Ebene:
{
  "scenarios": [
    {
      "name": "Neuanlage Artikel",
      "result": "PASSED",
      "duration": 4500,
      "steps": [
        {
          "order": 1,
          "keyword": "Given",
          "text": "I open an editor \"Artikel\" from table \"2:1\" with command \"NEW\"",
          "result": "PASSED",
          "duration": 1200
        },
        {
          "order": 2,
          "keyword": "Then",
          "text": "field \"such\" has value \"TEST001\"",
          "result": "FAILED",
          "duration": 150,
          "error": "Expected 'TEST001' but got 'TEST002'"
        }
      ]
    }
  ]
}

Runner-Ablauf:

EINGABE: Pfad zur .feature-Datei

1. Parse .feature-Datei → Feature-Name, Tags, Background, Scenarios mit Steps
2. Extrahiere GUID aus Tags → Finde CUCUMBER_RESULT über resGuid,
   oder lege neuen Datensatz an (mit GUID, Überschrift, Beschreibung)
3. Erstelle neue Testlauf-Zeile in der Tabelle

FUER JEDES Scenario:
  scenarioResult = PASSED

  // Background ausführen (Login)
  WENN testUser gesetzt:
    login(testUser)

  FUER JEDEN Step IN Scenario:
    startTime = now()
    VERSUCHE:
      Erkenne ActionType aus Step-Text (Pattern-Matching)
      Führe entsprechende abas-Operation aus
      stepResult = PASSED
    BEI FEHLER(e):
      stepResult = FAILED
      errorMsg = e.message
      scenarioResult = FAILED
      runFailedAt = "Scenario: {name} / Step {nr}: {text}"
      // Restliche Steps dieses Scenarios = SKIPPED
      ABBRUCH Scenario-Schleife
    ENDVERSUCH

4. Schreibe Ergebnis in Testlauf-Zeile (runDate, runResult, runDuration, ...)
5. Speichere CUCUMBER_RESULT → KPI-Neuberechnung wird ausgelöst

6.5.3 KPI-Berechnung (VorSpeichern EventHandler)

Wird beim Speichern des CUCUMBER_RESULT Datensatzes ausgeführt:

X = resKpiSampleSize (einstellbar, Standard 10)
letzteXLaeufe = Tabelle sortiert nach runDate DESC, erste X Zeilen

resKpiAvgDuration = DURCHSCHNITT(letzteXLaeufe.runDuration)
resKpiPassRate    = ANZAHL(letzteXLaeufe WHERE runResult = "Passed") / X
resKpiPassRateDisplay = "{Passed}/{X} ({PassRate * 100}%)"

// Beispiel: 9 von 10 bestanden → "9/10 (90%)"

// Trend: Vergleiche aktuelle X Läufe mit vorherigen X Läufen
vorherigeXLaeufe = Tabelle sortiert nach runDate DESC, Zeilen X+1 bis 2X
WENN vorherigeXLaeufe vorhanden:
  altPassRate = ANZAHL(vorherigeXLaeufe WHERE runResult = "Passed") / ANZAHL(vorherigeXLaeufe)
  WENN resKpiPassRate > altPassRate: resKpiTrend = "Besser"
  WENN resKpiPassRate = altPassRate: resKpiTrend = "Gleich"
  WENN resKpiPassRate < altPassRate: resKpiTrend = "Schlechter"

resLastRunDate   = letzteXLaeufe[0].runDate
resLastRunResult = letzteXLaeufe[0].runResult

6.5.4 Cron-Anbindung (automatische Testausführung)

Ein Cronjob ruft regelmäßig ow1.CUCUMBER_CRON auf, das Features anhand von Tags filtert und automatisch ausführt.

Ablauf:

CRONJOB ruft auf: ow1.CUCUMBER_CRON

1. Lese Cron-Konfiguration (Variablen ycukeCron*)
2. Scanne ow1/cucumber/features/
   - Filtere .feature-Dateien nach Tags (z.B. @nightly)
   - Schließe Tags aus (z.B. @manual, @wip)
   - Optional: Filtere nach Ordnern
3. FUER JEDES passende Feature:
   - Rufe ow1.CUCUMBER_RUNNER auf
   - Ergebnis wird in CUCUMBER_RESULT geschrieben
4. Schreibe Cron-Zusammenfassung in Cron-Historie-Tabelle des IS
5. Optional: E-Mail-Benachrichtigung bei Fehlern

Tag-basierte Filterung (Beispiele):

TagVerwendung
@nightlyNächtlicher Regressionslauf
@regressionRegressionstests nach Deployment
@smokeSchnelle Smoke-Tests (z.B. stündlich)
@manualWird vom Cron AUSGESCHLOSSEN
@wipWork in Progress — wird vom Cron AUSGESCHLOSSEN

Einzelne Features per GUID suchen und ausführen:

Aus anderen abas-Prozessen heraus kann ein einzelnes Feature gezielt über seine GUID angestoßen werden:

AUFRUF: ow1.CUCUMBER_RUNNER guid=a1b2c3d4-e5f6-...

1. Scanne alle .feature-Dateien
2. Finde Datei mit dem Tag "@guid-a1b2c3d4-e5f6-..." (eindeutig)
3. Führe nur diese aus
4. Schreibe Ergebnis in CUCUMBER_RESULT (Suche über resGuid)

Da die GUID eindeutig ist, wird immer genau eine Feature-Datei gefunden und ausgeführt.

7 Linux-Befehle zum Parsen der Feature-Dateien

Der Entwickler kann folgende Linux-Befehle verwenden, um Informationen aus den .feature-Dateien auszulesen:

Feature-Name (1. Zeile mit "Feature:"):

grep -m1 '^Feature:' /path/to/datei.feature | sed 's/^Feature: *//'

Beschreibung/Kommentar (Zeilen mit # nach der Feature-Zeile):

sed -n '/^Feature:/,/^[[:space:]]*$/{ /^[[:space:]]*#/{ s/^[[:space:]]*# *//; p; } }' /path/to/datei.feature

Tags (Zeilen die mit @ beginnen, vor Feature:):

sed -n '/^@/p; /^Feature:/q' /path/to/datei.feature | tr ' ' '\n' | grep '^@'

Anzahl Scenarios:

grep -c '^[[:space:]]*Scenario:' /path/to/datei.feature

Anzahl Steps (Given/When/Then/And/But):

grep -cE '^[[:space:]]+(Given|When|Then|And|But) ' /path/to/datei.feature

Background TestUser:

grep -oP 'logged in with password "\K[^"]+' /path/to/datei.feature

Alle Features in einem Verzeichnis mit Name, Tags, Scenario- und Step-Anzahl auflisten:

for f in /path/to/features/**/*.feature; do
  name=$(grep -m1 '^Feature:' "$f" | sed 's/^Feature: *//')
  tags=$(sed -n '/^@/p; /^Feature:/q' "$f" | tr '\n' ' ')
  scenarios=$(grep -c '^[[:space:]]*Scenario:' "$f")
  steps=$(grep -cE '^[[:space:]]+(Given|When|Then|And|But) ' "$f")
  desc=$(sed -n '/^Feature:/,/^[[:space:]]*$/{ /^[[:space:]]*#/{ s/^[[:space:]]*# *//; p; } }' "$f" | head -1)
  echo "$f | $name | $tags| Scenarios: $scenarios | Steps: $steps | $desc"
done

Feature-Datei per GUID suchen (eindeutig):

grep -rl '@guid-a1b2c3d4-e5f6' /path/to/features/ --include='*.feature'

GUID aus einer Feature-Datei extrahieren:

grep -oP '@guid-[a-f0-9-]+' /path/to/datei.feature | head -1

Feature-Dateien nach Tag suchen (z.B. @nightly):

grep -rlZ '@nightly' /path/to/features/ --include='*.feature' | xargs -0 -I{} basename {}

Feature-Dateien nach Tag suchen und ausführen (für Cron):

# Alle Features mit Tag @nightly finden
grep -rl '@nightly' "$MANDANT/ow1/cucumber/features/" --include='*.feature' | while read f; do
  guid=$(grep -oP '@guid-[a-f0-9-]+' "$f" | head -1 | sed 's/@guid-//')
  echo "Running: $f (GUID: $guid)"
  # Hier FOP-Runner aufrufen mit GUID
done

8 Offene Punkte / Entscheidungen

ThemaFrage
Step-ErkennungSoll der Runner die Steps per Regex aus dem Gherkin-Text erkennen, oder soll der Cucumbergenerator zusätzlich eine JSON-Datei (.feature.json) neben dem .feature ablegen?
MandantenfähigkeitSollen Tests auf verschiedenen Mandanten laufen können?
Parallel-AusführungKönnen mehrere Features gleichzeitig laufen (mehrere FOP-Sessions)?
Cleanup / RollbackSollen Testdaten nach dem Lauf aufgeräumt werden? (z.B. alle Datensätze mit Präfix "CUKE_" löschen)
Tabellen-LimitMax. Anzahl Testlauf-Zeilen pro CUCUMBER_RESULT? (Empfehlung: ab 100 Zeilen älteste archivieren)
Feature-VersionierungReicht Git-Versionierung, oder soll abas eine eigene Historie führen?
Mehrere Cron-SchedulesSollen mehrere Cron-Konfigurationen möglich sein (z.B. stündlich @smoke + nächtlich @regression)?
